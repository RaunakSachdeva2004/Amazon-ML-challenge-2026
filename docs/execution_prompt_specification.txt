2. Problem Statement
This is a multi-source entity resolution challenge. Business identity data arrives from 3 independent sources, each with partial, noisy fragments describing the same real-world entities, with no shared identifiers across sources.
Source 1 is the deduplicated reference source — one row per real-world business entity.
Source 2 and Source 3 are independent noisy sources that may contain zero, one, or many records matching any given Source 1 entity.
Task: for every Source 1 entity, find all matching records in Source 2 and Source 3 (a many-to-one-or-more relationship from S2/S3 → S1, expressed as one row per S1 entity listing all its matched S2/S3 ids).
Noise you must handle:
Name: abbreviations (Corp/Corporation, Pvt/Private, Ltd/Limited), legal-suffix inconsistencies, DBA/trade names, punctuation differences (& vs and), word-order transpositions, typos.
Address: abbreviations (Rd/Road, St/Street), transliteration variants, missing components (no PIN/ZIP, no state), landmark-based references ("Near SBI ATM"), municipal numbering-format differences, component reordering.
Training data covers US and India only. The test set additionally contains France, unseen in training. country must be treated as an open-set string label — never hardcode, filter, or one-hot-encode against only {US, India}. Every test entity, France included, must appear in the final submission.
There is no explicit "source" column: a record's source is determined entirely by the S1- / S2- / S3- prefix on its entity_id and by which file it was read from.

All files are tab-separated (.tsv). Business names and addresses may contain commas, so tabs are the delimiter. Always read with an explicit separator:

Reading without sep="\t" silently collapses everything into one column — always verify df.shape[1] > 1 after load as a sanity check.

6. Module: normalize.py
Build one function applied identically to business_name and business_address across all three sources — consistency across sources matters more than any single rule's cleverness.
Steps, in order:
Unicode NFKC normalization (handles transliteration/accent variants).
Lowercase.
& → and (and vice versa is not needed — pick one canonical direction).
Strip punctuation but retain a raw (unstripped) copy of every field alongside the cleaned one — edit-distance features may want raw text, token features want cleaned text.
Legal-suffix dictionary for business_name: map corp/corporation/co → corp; ltd/limited → ltd; pvt/private → pvt; inc/incorporated → inc, etc. Build this dictionary by inspecting actual value frequencies in the training business_name columns — do not invent entries you haven't observed. Produce two name fields: suffix-normalized, and suffix-stripped entirely (drop the tokens after mapping) — keep both, since presence/absence of a suffix is itself a weak feature.
Address abbreviation dictionary: rd→road, st→street, ave→avenue, apt→apartment, etc. — again, derive the dictionary from patterns actually observed in business_address values across the training data (inspect first), keep it general rather than country-keyed since France must go through the same function with no special-casing.
Lightweight address component extraction via regex only (no geocoding): pull out digit clusters that look like a PIN/ZIP code (varies by length/format across countries — detect by pattern, not a country lookup table), a leading street-number token, and treat the remainder as a free-text locality string. Store these as separate derived columns (postal_code_guess, street_number_guess, address_remainder) alongside the full normalized address — used for exact-match features in Section 8, not for imputing missing data.
Whitespace collapse and trim as the final step on every derived text field.
Output: a normalized dataframe per source with both raw and cleaned name/address columns, the suffix-stripped name variant, and the three address-component guess columns. Print null rates and a sample of before/after transformations for a subsample of rows as a sanity check before moving to blocking.
7. Module: blocking.py
Blocking sets the recall ceiling — implement all strategies below and union their outputs; do not rely on a single method.
Token inverted index: build an inverted index of significant business_name tokens (after suffix-stripping and stopword removal) per S2 and S3. For each S1 record, collect all S2/S3 records sharing ≥1 token, weighted by inverse document frequency so common tokens ("store", "the") don't create oversized blocks. Cap per-token posting-list contribution if a token is extremely common.
TF-IDF cosine over character n-grams (name): fit a TfidfVectorizer(analyzer="char_wb", ngram_range=(2,4)) (or similar) on normalized business_name across all sources, compute top-k nearest S2/S3 neighbors per S1 record via sparse matrix multiplication or sklearn.neighbors.NearestNeighbors(metric="cosine"). During validation experiments, learned vectorizers/statistics must be fitted only on the training partition; at final test inference they may be fitted using all available training sources.
TF-IDF cosine over address: same approach applied to normalized business_address.
Sorted neighborhood: sort all records by a normalized name key (e.g., first N characters of the cleaned, suffix-stripped name), slide a fixed-width window, and add nearby S2/S3 records as candidates for each S1 record in the window — this catches word-order transpositions that token/n-gram blocking can miss.
Phonetic blocking (secondary pass): apply Soundex or Metaphone to the first significant name token; block records sharing a phonetic code. Use a pure-Python implementation (e.g. jellyfish) — no external service.
Combination: union candidates from all five strategies per S1 entity, keep each strategy's raw similarity score as a separate numeric column (do not discard them — feed them into Section 8 as features), then test 20 / 40 / 60 / 100 candidates → measure blocking recall + runtime + validation F0.5, then select the optimal cap based on those measurements so the downstream classifier stays tractable.
Do not hard-filter by exact country match. Country agreement is a soft signal, computed later as a feature (Section 8) — always compute textual candidates across country boundaries too, since France has no training examples and must rely purely on textual similarity to surface candidates at all.
Required self-check: on a held-out slice of the training ground truth, measure blocking recall = (fraction of true S1↔S2/S3 matches that survive the union of all blocking strategies). Print this number. If it is materially below ~95%, loosen top-k or add a blocking key before moving on — this ceiling cannot be recovered by the classifier later.
Output of this module is exactly the object that becomes candidate_pairs.tsv after Section 11 writes it — the same candidate set the classifier in Section 9 will score, not an earlier, looser pass you filter further downstream.
8. Module: features.py
Compute one feature vector per (S1 id, candidate id) pair produced by blocking.py.
Name features:
Normalized Levenshtein distance (raw name and cleaned name)
Jaro-Winkler similarity
Token Jaccard and Dice coefficient (cleaned, tokenized name)
TF-IDF cosine — char n-gram and word n-gram variants
Token-sort ratio and token-set ratio (order-invariant; catches transpositions) — via rapidfuzz or equivalent
Absolute and relative name length difference
Acronym match flag: does one side's first-letters sequence equal the other side's short form?
Suffix-stripped-name exact-match flag
Address features:
Same similarity suite (Levenshtein, Jaro-Winkler, Jaccard, cosine) on normalized address
Postal-code exact-match flag (only when both sides' postal_code_guess is non-null)
Street-number exact-match flag
Longest common substring length (normalized)
Address length ratio
Meta / structural features:
Country-match flag (same/different string) — never used as a hard filter, only a feature
Source-pair indicator (S1×S2 vs S1×S3) — patterns may differ by source
Each blocking strategy's raw similarity score from Section 7 (do not drop these)
Candidate rank within its S1 entity's block (1 = closest by blocking score)
Optional (Tier 2, only if time remains after Sections 9–11 are working end-to-end): a local open-weight sentence-embedding model (MIT/Apache-licensed, ≤8B params, run fully offline — see Section 13 for the default choice) embedding cleaned name/address text, with cosine similarity between S1 and candidate embeddings as one additional feature column. This is additive on top of the string features above, never a replacement for them.
Output: one row per candidate pair with all feature columns plus source1_entity_id and candidate_entity_id as join keys, ready for Section 9.
9. Module: train_model.py
Label construction: from train_ground_truth.tsv, join against the blocking output on (source1_entity_id, candidate_entity_id). A pair is a positive (label 1) if it appears in the exploded matched_entity_ids list; every other pair that blocking retrieved for that S1 entity is a negative (label 0). Use these blocking-derived negatives — do not sample random negatives — since they are the actual decision boundary the classifier needs to learn (hard negatives).
Split strategy: Create one fixed, reproducible S1-level train/validation split before fitting any learned component. Use this same split for blocking-recall measurement, classifier validation, calibration, threshold tuning, and final reported F0.5. Fit TF-IDF/vectorizers/blocking statistics on the training portion only where applicable.
Model: LightGBM binary classifier (objective="binary"), MIT-licensed, well under the 8B-parameter cap. Use scale_pos_weight or is_unbalance=True to address the heavy class imbalance (most candidate pairs are non-matches). Reasonable starting hyperparameters: num_leaves=31, learning_rate=0.05, n_estimators=500 with early stopping on validation AUC-PR (not accuracy), max_depth=-1. Tune from there only if time allows — do not spend excessive time on hyperparameter search before Sections 10–11 are working end-to-end.
Hard-negative mining (Tier 1 refinement — do this once you have a working baseline): Run the baseline on the training portion using cross-validation or out-of-fold predictions, identify high-confidence false positives there, add those as hard negatives, and evaluate the resulting model once on the untouched validation partition.
Evaluation during training: monitor precision-recall curve on the grouped validation split, not plain accuracy or AUC-ROC — the competition metric is precision-heavy (Section 12 has the exact formula). Save the trained model and the validation predictions (scores + true labels + entity ids) to disk for use by Section 10's threshold tuning.
10. Module: decode.py
This stage matters as much as model choice — F_0.5 is precision-weighted (β=0.5) and macro-averaged per S1 entity, with correct singleton prediction scoring a full 1.0. Do not use a fixed 0.5 cutoff without tuning. The ground-truth matching lists are sets, so ordering of matched IDs is irrelevant to scoring. A prediction containing an incorrect extra ID counts as a false positive and therefore reduces precision.
Compare raw LightGBM scores against calibrated scores. Keep calibration only if it improves grouped validation F0.5 under a nested or separate calibration procedure. Otherwise use raw scores.
Threshold sweep: on the grouped validation split, compute the exact F_0.5 macro-average (Section 12's formula) for a grid of thresholds (e.g. 0.05 to 0.95 in steps of 0.01). Select the threshold that maximizes validation F_0.5. Because false merges are penalized 2× more than misses, expect the optimal threshold to sit meaningfully above 0.5 — do not assume 0.5 is near-optimal.
Per-entity decoding: for each S1 entity, keep only candidates whose calibrated score exceeds the tuned threshold. If none exceed it, emit an empty match list (a correctly predicted singleton scores 1.0).
Confidence-gap rule (apply if it improves validation F_0.5 — test empirically, do not assume): when the top candidate's score is only marginally above the threshold, or only marginally above the second candidate's score, prefer emitting fewer matches — a marginal-confidence inclusion typically hurts precision more than a marginal-confidence omission hurts recall under this metric.
Persist the exact threshold(s) and calibration parameters used, so write_outputs.py (Section 11) applies identical logic to the test set as was validated in Section 12.
Output: a per-S1-entity list of accepted candidate ids, ready to be written as matching_results.tsv.

12. Module: evaluate.py — Local F_0.5 Harness
Implement this exactly, since it is the only ground truth you have for judging every decision above (no leaderboard access during offline development):
def f0_5_per_entity(predicted_ids: set, true_ids: set) -> float:
    if len(true_ids) == 0:
        return 1.0 if len(predicted_ids) == 0 else 0.0
    if len(predicted_ids) == 0:
        return 0.0
    tp = len(predicted_ids & true_ids)
    precision = tp / len(predicted_ids)
    recall = tp / len(true_ids)
    if precision == 0 and recall == 0:
        return 0.0
    beta = 0.5
    return (1 + beta**2) * precision * recall / (beta**2 * precision + recall)

def macro_f0_5(predictions: dict, ground_truth: dict) -> float:
    # predictions, ground_truth: {source1_entity_id: set(matched_ids)}
    scores = [f0_5_per_entity(predictions.get(sid, set()), true_ids)
              for sid, true_ids in ground_truth.items()]
    return sum(scores) / len(scores)
